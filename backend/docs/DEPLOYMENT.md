# Deployment readiness — no deployment performed

Business logic and Prisma schema are portable. For Azure App Service/Container Apps or another Node host: build with locked dependencies, generate Prisma, compile TypeScript, run `node dist/src/main.js`; configure PORT, API_PREFIX, production NODE_ENV and explicit browser CORS origins. Inject secrets through managed configuration/Key Vault, never Flutter, images or repository files. Serve the API through HTTPS; release Android rejects cleartext. Configure Flutter's HTTPS API_BASE_URL at build time.

Azure Database for PostgreSQL requires a supported PostgreSQL version, restricted networking/firewall/private endpoint, verified TLS certificate configuration, backups and an explicit capacity plan. Use `sslmode=verify-full` with a trusted CA/driver configuration appropriate to the provider; never disable certificate verification. Allow the trusted `pg_trgm` extension before applying the migration. The current development owner role is not a production runtime permission policy: create separate migration owner and least-privilege runtime role (SELECT only for this phase). Future writes receive scoped grants only when required.

Use a direct connection for DIRECT_URL migration jobs; DATABASE_URL may target an approved pooler. Run `prisma migrate deploy` once as a release job after reviewing SQL/backups, then start replicas. Never run migrate reset/db push in production. Check schema drift separately; migrate deploy does not replace drift auditing. Coordinate backwards-compatible schema/API changes and migrations before releasing mobile clients.

Pool max 5 is per process: replicas × pool size plus migration/admin connections must fit the server budget. Start small and measure; tune query/connection/statement timeouts centrally. Current `/api/v1/health` checks DB readiness and returns 503 on failure. Configure ingress request timeouts above the 8s application timeout, HTTP rate/request limits, readiness checks, graceful SIGTERM and sufficient shutdown grace. Add a separate process-liveness endpoint if the platform needs to distinguish DB outages from a wedged process. No load capacity is claimed from sample data.

Logs are JSON to stdout with request correlation IDs, duration and status. Configure collection/retention and alerts for 5xx, latency, pool saturation and failed migrations; do not collect passwords, tokens or arbitrary request bodies. Add authentication/authorization before any operator/admin writes. Swagger is disabled in production. Rate limiting, threat review, TLS ingress, release signing and secret rotation remain deployment tasks.

Use managed automated backups/PITR and rehearse restores into a separate database. For a local-to-cloud move use matching PostgreSQL tooling: `pg_dump --format=custom --no-owner --no-acl` with a secure password prompt/passfile and `pg_restore --no-owner --no-acl` into an empty approved destination, then verify counts/checksums, migration history, roles and constraints. Do not put passwords in shell arguments. Restrict/encrypt dump files; they may later contain personal data. Test extension/version compatibility and restore before cutover. Take a fresh backup before production migration, document rollback/forward-fix plans and do not overwrite an unrelated database.
