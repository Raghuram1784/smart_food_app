# Catalog schema and pricing foundation

Twelve catalog tables: Restaurant, Category, Cuisine, RestaurantCuisine, MenuSection, MenuItem, MenuItemVariant, AddOn, MenuItemAddOn, DeliveryZone, RestaurantDeliveryZone, PricingRule. Prisma additionally owns `_prisma_migrations`.

Restaurant → sections/items is one-to-many. Category → items is one-to-many. Restaurant ↔ Cuisine and MenuItem ↔ AddOn use explicit joins with composite primary keys. MenuItem references both sectionId and restaurantId, so a section from another kitchen cannot be assigned accidentally. Item variants reference their parent. Restaurant ↔ DeliveryZone describes explicit eligibility; absence means unknown/ineligible, never worldwide coverage. Optional PricingRule scopes reference restaurant/zone. All business foreign-key deletions are restricted rather than cascading into important records.

Stable original IDs and image keys are preserved. Slugs/category names are unique. Non-null fields, enum statuses, nonnegative item/add-on/variant prices, positive version/delivery minutes, rating bounds, valid coordinate pairs, pricing-rule XOR/range/date checks are enforced in PostgreSQL. Review counts/coordinates are nullable because no valid original values exist. SQL numeric ratings/coordinates are converted to JSON numbers; money remains integer paise. Menu availability has a reason, timestamp and version, not fictitious inventory.

Seed reads `prisma/catalog.json`, extracted from the original Dart fixture. Upserts use empty updates: repeat execution adds missing required records but does not replace existing edits or delete unrelated rows. All seed work is transactional. Known dietary values derive from descriptions (pepperoni/bacon/beef are nonvegetarian). South/North Indian cuisine links classify the preserved Indian menu. Fictional Bengaluru zones have no seeded eligibility associations. No invented variants, add-ons, fee rules or reviews.

Indexes cover IDs/slugs, reverse join keys, restaurant/availability/display order, category/availability/price and section ownership. pg_trgm GIN indexes cover menu name/description and restaurant name/cuisine description for substring search. Query includes batch related records instead of a per-row service loop. Pool max 5 per process; DB statement timeout 5s, client query timeout 6s, API 8s. Representative EXPLAIN is exercised in integration tests; a tiny 8-row catalog is not a scale benchmark. Re-evaluate joins, indexes and cursor pagination with realistic data before launch.

## Planned exact pricing policy (not an implemented checkout)

PricingRule supports PACKAGING, DELIVERY, PLATFORM, DISCOUNT and TAX; choose exactly one fixedPaise or rateBasisPoints, optional cap, minimum subtotal, effective interval and promotion eligibility code. Rules default inactive. Variant adjustments are nonnegative surcharges in this foundation; discounts use explicit rules.

Future quote algorithm: derive item subtotal from authoritative base/variant/add-on values times validated integer quantity; validate availability/zone first. For each component choose the eligible rule with the most-specific scope (restaurant+zone, restaurant, zone, global), then highest priority, then ascending stable code as deterministic tie-break. Do not stack rules implicitly. Promotions additionally require authenticated eligibility checks and usage limits. Freeze the chosen IDs/version and inputs in a quote snapshot.

Evaluate packaging, delivery, platform, then discount; clamp discount to its documented eligible item subtotal, then calculate each tax component against an explicitly configured taxable base. Before enabling multiple simultaneous taxes extend rule identity with a tax-component code and jurisdiction; the present single TAX placeholder is not a tax engine. Never assume legal tax rates from the demo. Percentage rounding uses integer HALF_UP: `(basePaise * basisPoints + 5000) / 10000`, integer division, once per component; use bigint intermediates/checked bounds. Apply caps after rounding; total cannot go below zero. A quote response must list every amount, validity time and policy version. Orders later freeze this breakdown; later catalog/rule edits must not rewrite historic money.

Migration `202611110001_catalog/migration.sql` contains actual Prisma-generated DDL followed by reviewed CHECK constraints and trigram indexes. New changes get new migrations; never edit an applied migration.
